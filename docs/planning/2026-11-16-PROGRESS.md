## 2. Task C · 无线能力体检

**一条命令**：

```bash
uv run python -m wifit3.wireless_capabilities        # 人读表格
uv run python -m wifit3.wireless_capabilities --json # 机读
uv run python scripts/capability_probe.py            # dev 包装
```

**三层结论**（决定后续动作完全不同，因此分开）：

| verdict | 含义 | 处置 |
|---|---|---|
| `driver_unsupported` | 无无线接口 / 驱动未绑定 | 装驱动 |
| `hardware_lacking` | 无可用 PHY，也未上报能力 | 换硬件 |
| `firmware_refused` | 驱动与固件正常，能力自报为无 | 用户态无法绕过，只能换硅片 |
| `passive_only` | 有 monitor 无 TX（iwlwifi / Windows） | 只可嗅探 |
| `injection_capable` | monitor + raw TX（Linux 已知主动驱动） | 全功能 |

**本机实测结论**：`Intel(R) Wireless-AC 9462` → `firmware_refused`，判据逐条引用 `netsh` 原文
（`网络监视模式 : 不支持`、`混杂模式 : 不支持`、`软 AP : 不支持`、`IBSS : 不支持`，
`动作帧 : 支持`）。

**平台事实（写进报告，避免误导）**：Windows WDI 对任何网卡都不向用户态暴露 802.11 monitor
mode，因此「网络监视模式：不支持」是 WDI 栈的共性回答。这也解释了为什么本机装了 Npcap
（`C:\Windows\System32\wpcap.dll`）也只能被动抓包、不能注入。

**解析器是纯函数**：中英文 `netsh` 快照、Linux `iw list` / `iw dev` 都有离线测试，不需要目标硬件。

## 3. Task A · 虚拟 802.11 适配器

**为什么不动 `Driver` ABC**：新增 `chips/sim/` 走既有 pkgutil 发现机制，符合
`docs/porting/METHODOLOGY.md`「What a port may edit」。合成设备走
`device/backend.py::set_usb_backend_factory()` 这个官方钩子，默认不启用。

| 模块 | 职责 |
|---|---|
| `chips/sim/radio.py` | 合成射频：虚拟 AP、信标、auth/assoc/M1 应答、PMKID 推导 |
| `chips/sim/driver.py` | `SimulatedDriver(Driver)`：RX/TX 通路，无 USB 流量 |
| `chips/sim/backend.py` | `SimulatedUsbBackend` + `use_sim_backend()` / `reset_usb_backend()` |
| `chips/sim/__init__.py` | `SUPPORTED_IDS` + `import_driver`（`0x5e1a:0x0001`，未分配 VID） |

**可破解性是真的**：虚拟 AP 用 `derive_pmk(psk, ssid)` + `pmkid(pmk, ap, sta)` 生成 M1 的
PMKID KDE，与 hashcat `-m 22000` 复算的是同一个值。端到端测试断言：采到的 PMKID 用该 PSK
验证为 `True`、用错误 PSK 为 `False`。

**实测产物**（一次真实运行）：

```
AP: 02:00:5e:1a:00:01 sim-lab-2g WPA2-PSK-CCMP [2]
pmkid: ecbc6dcfdc3fe6787cb0110a7e76ebc9
hc22000: WPA*01*ecbc6dcfdc3fe6787cb0110a7e76ebc9*02005e1a0001*02c820dc8343*73696d2d6c61622d3267***
cracks with known psk: True | wrong psk: False
```

**用法**：

```python
from wifit3.chips.sim.backend import use_sim_backend, reset_usb_backend
use_sim_backend()      # devices() / wlan_iface() 立刻能看到虚拟网卡
...
reset_usb_backend()    # 恢复真实 libusb
```

**两个刻意的设计决定**：

1. **送达延迟 3 ms**：真实驱动的帧经 RX 线程到达，永远不会在 `inject_frame()` 调用内同步返回。
   `Association._send_until` 在发送后立刻 `clear()` 应答事件，同步回帧会被清掉，所以虚拟射频
   也异步投递。
2. **`import_driver` 用赋值而非 `def` 声明**：`tests/chips/test_inject_frame.py` 与 ACK 台架会
   枚举所有"声明了驱动工厂"的包，并在 USB 描述符录波器上构造驱动；无 USB 的虚拟驱动不适用。
   发现机制读的是属性，赋值不影响 `supported_ids()`。

## 4. Task B · 板载 CNVi 探测

**结论先行**：CNVi 网卡**无法**进入 `supported_ids()`。`DeviceID` 带的是 USB `vid:pid`，
每个驱动都要 `usb.core.Device`；而 CNVi 的 Wi-Fi 功能在 USB 上根本不存在。要强行接入必须改
`Driver` ABC，`METHODOLOGY.md` 明令 port 不许改，需 `derv82` 同意。

因此本项交付的是**诚实的旁路呈现**，没有假装成可用网卡：

```bash
uv run python -m wifit3.device.host_radios
```

本机实测：

```
Intel Wireless-AC 9462
  pci       : 8086:a0f0  subsys 8086:42a4
  driver    : Netwtw10.sys
  kind      : cnvi  (wifit3 reach: passive)
  note      : CNVi: the 802.11 MAC, baseband and firmware are inside the PCH ...
  note      : The USB device beside it (8087:0aaa) is the Bluetooth half ...
  note      : Firmware refuses monitor mode and injection on this family ...
```

只有**实测确认过**的 PCI id 才断言 CNVi（当前仅 `0xa0f0`）。未在表内的 Intel 无线 id 一律
`unknown`，不猜架构。
